# Home-built film LUT provenance

The app ships three stocks: **250D / 5207**, **500T / 5219** and
**Ektachrome 100D**. The following original-generation record covers the two
negative stocks; the reversal generation is documented separately below.
The two negative stocks use common
name then emulsion number, as printed on the canister. Both look-up tables are
generated by this project on a fixed Kodak Vision 2383 print stage. The 50D and
200T stocks and their externally-produced tables have been removed (git history
retains them).

## What these tables are

- **Input domain**: Apple Log 2 encoded code values in Apple Wide Gamut, `[0,1]`
  per channel — i.e. what the camera records. The camera locks white balance to
  the stock's temperature, so the input is already balanced.
- **Output**: Rec. 709 gamut, gamma 2.4 encoded, matching the preview layer's
  `CGColorSpace.itur_709` tag.
- **Size**: 33³, red-fastest row order (`row = r + g·33 + b·33²`), the convention
  the app's `.cube` parser and 3D texture upload use.
- Colour response only. Grain, halation and glow stay in the render pipeline and
  are not baked into the cube.

## Source

Negative and print stages come from **Spectral Film LUT** by Jan Lohse, MIT
licensed, commit `6307a98f3cf4f2d7b6d09bab82fbf6f64356ccfe`:

- <https://github.com/JanLohse/spectral_film_lut>
- Film data: `Kodak Vision3 250D 5207` (2009), `Kodak Vision3 500T 5219` (2007),
  print `Kodak Vision 2383/3383` (1998), digitized from manufacturer datasheets
  by that project.
- That project documents its own limits, which carry over: published datasheet
  precision varies, long-discontinued formats are worse, and interlayer effects
  use simplified assumptions.

The Apple Log 2 transfer function and Apple Wide Gamut primaries come from
Apple's published Apple Log 2 profile via OpenColorIO v2.6.0 (BSD-3-Clause),
`src/OpenColorIO/transforms/builtins/AppleCameras.cpp`. Log 2 shares the Apple
Log curve and differs only in primaries.

## Generation parameters

The film stages receive CIE XYZ, so no Apple-Log-aware colour library is needed
inside the simulation.

| Parameter | Value |
|---|---|
| grid | Apple Log 2 code values `[0,1]`, 33³ |
| decode | Apple Log curve (OCIO constants) → linear Apple Wide Gamut |
| gamut | Apple Wide Gamut RGB → XYZ (D65) |
| confinement | chromaticities outside the CIE 1931 spectral locus pulled onto it |
| pipeline | `mode="full"`, negative → 2383 print → projection |
| `input_colorspace` | CIE XYZ (`None`) |
| `exp_kelvin` | **6504** |
| `color_masking` | stock default (1.0 for these Status-M negatives) |
| `output_gamut` / `gamma_func` | Rec. 709 / Gamma 2.4 |
| `white_clip` | on |
| filter | generator's "oversampling" (2N−1 grid, 3×3×3 median, decimate) |

**Why `exp_kelvin = 6504`.** The pipeline's `exp_kelvin` describes the
illuminant of a *raw* scene. Our input is already white-balanced by the camera,
so calibrating for the stock's own temperature (5500 K, 3200 K) tilted the
sensitivity and produced a large cast on neutral tones — measured mid-gray
spread 0.067 and 0.062 against 0.004 at the neutral reference.

**Why the spectral-locus confinement.** Apple Wide Gamut's blue primary is
imaginary (y = −0.076), so **49.3%** of the Log 2 cube's knots decode to a
colour outside the CIE 1931 spectral locus — some with a negative XYZ component,
others with positive XYZ but an impossible chromaticity such as (0.115, 0.014).
The generator's spectral upsampling is a 2D LUT over chromaticity and is only
meaningful inside the locus; outside it the least-squares reconstruction is
unstable and neighbouring knots jumped **0.83** apart in output, producing
near-black holes beside bright knots in saturated blues. Pulling those
chromaticities onto the locus along the white-point ray at constant luminance —
**56.7%** of knots, with in-locus colours left bit-exact — cut the worst
adjacent-knot step to 0.63/0.55 and the 99.9th percentile to 0.34/0.33. The
tables used previously measured 0.30–0.38 and 0.21–0.25 on the same metric.

## Measured behaviour

From the packaged tables (33³, parsed in the app's row convention):

| Check | 5207 | 5219 |
|---|---|---|
| size / non-finite values | 33³ / 0 | 33³ / 0 |
| value range | 0.025–1.000 | 0.023–1.000 |
| neutral axis monotonic | yes | yes |
| mid-gray (Log 2 code 0.5) | 0.539 / 0.535 / 0.531 | 0.541 / 0.536 / 0.532 |
| neutral spread at mid | 0.008 | 0.009 |
| neutral spread at code 1.0 | 0.054 | 0.054 |
| max adjacent-knot step | 0.626 | 0.547 |

The residual spread at the ends of the neutral axis is film crossover in the toe
and shoulder, not a miscalibration.

`LUTSamplingTests` compares the GPU LUT kernel against an independent CPU
trilinear reference at 0.001 tolerance and passes for both shipped tables.

## Scope and limits

- These are **generated approximations of a film look**, not Kodak products, not
  Kodak-authorised, and not colorimetric calibrations of a camera or display.
  "5207", "5219" and "2383" identify the emulated emulsions descriptively.
- Numerical checks establish structure, domain, monotonicity, smoothness and GPU
  sampling agreement. They do not establish that the look is pleasing or correct
  — that needs eyes on real footage.
- The generation script is checked in under `tools/lut-generation/`, with its
  dependency pins and the upstream commit it was run against, so the tables can
  be rebuilt rather than taken on trust. See that directory's README.

## Ektachrome 100D reversal addition

The supplied upstream `reversal_film/kodak_ektachrome_100d.py` is already present
at the existing source pin `6307a98f3cf4f2d7b6d09bab82fbf6f64356ccfe`. Its contents
matched upstream main when fetched for this addition (source SHA-256
`88af6a98fdd32643eed66e76db98486940753355668ff005a9077192ed9bd00e`).
The model is `KODAK_EKTACHROME_100D`, **not** the alternate 2024 dataset in that
module. This is descriptive emulation, not Kodak-authorised calibration.

Kodak's 5294/7294 datasheet specifies daylight **5500 K, EI 100**; this catalogue
entry uses 5500 K and ISO 100. Source:
<https://www.kodak.com/content/products-brochures/Film/KODAK-EKTACHROME-100D-COLOR-REVERSAL-FILM-5294-7294-datasheet-EN.pdf>.
The upstream model labels its medium `photo`; using its colour model in this
shared photo/video pipeline is an approximation, not proof of identical output
from every physical Ektachrome format.

The Log 2 / Apple Wide Gamut input, confinement, neutral 6504 K exposure
reference, Rec.709/gamma-2.4 output and oversampled 33³ bake are shared. Reversal
projects directly with **no print film**. It does not acquire a 2383 stage or
negative inversion. Projection retains upstream defaults (6500 K,
`white_balance=1`, `white_clip=True`); no custom neutral-axis correction is baked.

Only Ektachrome uses upstream **Mallett 2019** spectral reconstruction. With
SFL reconstruction its largest adjacent-knot jump was **0.8349222** and p99.9
**0.6712483**, including discontinuities between saturated-purple chromaticities
inside the spectral locus. Mallett reduces those to **0.3286772 / 0.2705281**,
without changing the supplied film sensitivity or density curves. These metrics
use the maximum absolute RGB-channel change per neighboring cube edge, over all
three grid axes. `verify_cubes.py` rejects the SFL candidate with a real failing
assertion and accepts the shipped table; its thresholds are 0.35 and 0.29.

Measured from the written, red-fastest cube:

| Check | Ektachrome 100D |
|---|---|
| size / non-finite values | 33³ / 0 |
| value range | 0.0165865–1.0000000 |
| neutral axis | monotonic |
| Log 2 code 0.5 RGB | 0.5029852 / 0.5605509 / 0.5798431 |
| maximum neutral spread | 0.0768579 |
| max adjacent-knot step / p99.9 | 0.3286772 / 0.2705281 |

The cool midtone crossover is retained from this model, **not** claimed to be
neutral or colorimetrically matched to a photographed film chart. Reversal has
finite highlight latitude: upper cube neutrals reach a white plateau rather than
the negative/2383 shoulder. Tests retain highlight detail below that plateau
instead of rebaking this stock to pass negative-stock golden tolerances.

The app's separate halation/glow presets initially reuse the 250D settings;
`grainSize=1.0` and `outputContrast=1.0` are authored starting values. Gauge-owned
grain behaviour is unchanged. These spatial parameters are not measurements of
this physical reversal emulsion. Real-footage aesthetic acceptance is separate
from numerical and build checks.

Both resource copies have SHA-256:


A clean native-arm64 Python 3.12 bootstrap and subsequent regeneration reproduced
the original two negative-stock cubes byte-for-byte; neither installed negative
cube was replaced. The final Ektachrome table is regenerated and compared against
both installed resource copies before delivery.
