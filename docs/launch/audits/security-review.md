# Nitrate pre-launch source security, privacy and release-risk audit

**Snapshot:** local `150ca6f`; read-only examination of the tracked tree. Severity: **Critical 1, High 3, Medium 7, Low 2**. These are mixed *release, privacy and reliability* findings, not 13 remotely exploitable vulnerabilities. No claim of a secure build or App Store acceptance. `docs/prioritization.md` was already dirty and was not touched.

## Highest-priority findings

1. **Critical — advertised OS range cannot record (release functionality).** `project.yml:4-5` declares iOS 17.0, while `App/Modules/CameraCapture/CameraSession.swift:784-786` refuses the writer before iOS 27 and `App/Modules/CameraCapture/CameraSampleBufferRecorder.swift:924-929` repeats the gate; the Apple Log 2 capture gate is also iOS 26+ (`CameraSession.swift:1706-1710`). **Precondition:** install on any declared iOS 17–26 device, assuming the app can install. **Impact:** capture cannot complete, rather than a security bypass. **Fix:** align deployment target/device capability with actual feature availability or provide a supported capture fallback; explicitly test start/finish on minimum *advertised* OS and iOS 27. Also inspect the archived Info.plist deployment version. Source gates are certain; installability was not device-tested.

2. **High — original Log footage sent to Photos despite opt-out (privacy).** `App/Modules/FilmStockLibrary/FilmStockConfig.swift:277-283,310-315` defaults `saveOriginalLog` to false. Normal successful delivery respects it (`App/Modules/RenderQueue/RenderQueueViewModel.swift:234-240`), but render failure invokes `saveOperation(sourceURL)` unconditionally (`:281-305`); a readable take rejected by validation routes `CameraViewModel.swift:735-742` → `ContentView.swift:152-157` → `RenderQueueViewModel.swift:327-343`, likewise independent of preference. Production `saveOperation` adds the video via Photos add-only authorization (`RenderQueueViewModel.swift:69-75,362-373`). **Preconditions:** user did not elect original export; render or validation fails; Photos add access is granted or user grants it at prompt. **Impact:** original sensitive material leaves the app sandbox into the user's Photos library, with any library synchronization/account policies; not evidence of third-party upload. **Fix:** decouple retention/rescue from export; ask explicit consent to export originals on failure, keeping them recoverable in-app otherwise. **Validate:** both fault paths with preference false and an injected Photos-save spy; assert zero original-save calls, plus explicit opt-in test.

3. **High — captured media can be cancelled/deleted on recording faults (original-media safety).** `CameraSampleBufferRecorder.swift:172-181` turns three drops into `fail`; video/audio backpressure or append failures (`:447-453,:537-543`) and ordinary stop-drain timeout (`:585-599`) also reach `fail`, which calls `writer.cancelWriting()` (`:722-735`). Failed output not wrapped as a retained finalized recording is removed at `:749-755`. **Precondition:** frames already accepted, then writer/device stalls, drops or fails before finalization. **Impact:** a partially recorded take may be lost rather than retained for rescue; this is reliability/media-loss risk, not attacker-controlled file deletion outside the app. **Fix:** on quality faults attempt bounded writer finalization and AVAsset readability validation, retain readable partial with visible warning; only delete demonstrably unusable files. **Validate:** inject writer/frame drops, append failure and drain timeout after accepted frames, then assert retained playable original, no clean-success label and one terminal callback.

4. **High — missing tracked privacy manifest for observed required-reason API use (release compliance).** `project.yml:93-107` packages app source/resources, but `git ls-files` finds no `PrivacyInfo.xcprivacy`. Code uses `UserDefaults` (`StockLoader.swift:13-24`), volume capacity (`CameraViewModel.swift:690-698`) and `ProcessInfo.systemUptime` (`CameraSampleBufferRecorder.swift:162-169`). Apple requires covered API categories/reasons declared in a bundled manifest and says absent declarations block App Store Connect submissions. [Apple: required-reason APIs](https://developer.apple.com/documentation/bundleresources/describing-use-of-required-reason-api) **Precondition:** submission of an archive containing these calls without a suitable manifest (a generated/untracked archive manifest is unverified). **Fix:** inventory all covered calls and add accurate reasons to app target resources, not invented generic declarations. **Validate:** inspect archived bundle and Xcode privacy report, then App Store Connect validation. This is not itself proof of tracking or data collection.

## Additional findings

5. **Medium — production render creates unrequested residual frame images (privacy).** `RenderQueueViewModel.swift:257-265` calls `dumpFrames` after every completed production render, writing up to three PNGs into `Documents/frames/<job UUID>` (`:376-396`); `remove(jobId:)` removes metadata only (`:129-136`). **Precondition:** any completed rendered video. **Impact:** extra frame copies remain after queue-row removal, increasing private-media/backups/storage exposure; no evidence of sandbox escape or network transmission. **Fix:** eliminate in Release or make explicit opt-in diagnostics with retention cleanup and appropriate backup policy. **Validate:** render under Release, remove job, inspect Documents and device backup scope.

6. **Medium — queue persistence failures do not stop delivery (duplicate/lost delivery).** `RenderQueueViewModel.swift:109-114,147-159,180-216` records persist errors but still starts processing and invokes Photos save before a durable completion marker; `QueuePersister.swift:18-21` writes atomic JSON. **Preconditions:** full storage or write failure, then app termination/relaunch. **Impact:** lost recovery entry or duplicate Photos asset after crash in save-before-marker window; original remains locally if not separately deleted. **Fix:** block state transitions on failed persistence or implement a recovery journal/idempotent delivery reconciliation. **Validate:** fault-inject every persistence transition and kill/relaunch at each save boundary, inspecting actual Photos asset count and queue recovery.

7. **Medium — failed-validation original has no durable rescue entry (discoverability/media recovery).** `CameraViewModel.swift:735-742` deliberately excludes a retained take from the queue; `ContentView.swift:152-157` clears the view-model reference immediately after a fire-and-forget `saveOriginal` (`RenderQueueViewModel.swift:327-343`). The MOV remains in `Application Support/Originals` (`CameraOriginalStorage.swift:8-17`), but a Photos-denied/failed save has only an in-memory error and no persisted retry row. **Preconditions:** readable failed take, Photos denied/save failure, app restart. **Impact:** footage is retained on disk but effectively undiscoverable through the current UI. **Fix:** persist rescue record before clearing reference and expose retry/export; test deny/restart/recover exact file.

8. **Medium — configured microphone can produce a clean video-only success (integrity).** `CameraSession.swift:369-380` marks mic added before confirming audio-output attachment; `CameraSampleBufferRecorder.swift:675-683` rejects zero audio samples only inside `#if DEBUG`, while output validation checks audio only if samples were appended (`:882-896`). **Precondition:** mic configuration expected but attachment/samples fail in Release. **Impact:** user believes audiovisual original was captured when audio is missing. **Fix:** verify output attachment and require audio evidence in production, retaining readable video as warned partial. **Validate:** Release device/test harness with mic configured and zero samples.

9. **Medium — purchase/trial does not guard functionality (commercial entitlement, conditional).** `ContentView.swift:141-150,216-223` enqueues renders and `CameraViewModel.swift:306-329` starts recording without a purchase/trial check. Trial date is local `UserDefaults` (`StoreManager.swift:101-115`). **Precondition:** app is intended to restrict functionality after trial/without purchase; whether a free-camera policy is intended is not established. **Impact:** no enforceable paywall in observed capture/render paths, local trial date alterable on a compromised device. **Fix:** specify free versus paid policy and gate appropriate entry points on freshly verified StoreKit state with an offline rule. **Validate:** expired, unpurchased, revoked, offline and lifetime cases on device. Not a security vulnerability if access is deliberately free.

10. **Medium — StoreKit entitlement state can stay stale (purchase correctness).** `StoreManager.swift:19-29,96-99` only sets `isPurchased = true` and does not reset it before enumerating current entitlements or restrict handled IDs; `PurchaseViewModel.swift:54-58` offers “Restore Purchases” but only rechecks local current entitlements. **Preconditions:** expiration/refund while manager lives, or restoration needing store synchronization. **Impact:** stale unlocked display or unsuccessful restore. **Fix:** recompute from verified, expected product IDs on refresh and transaction updates; invoke `AppStore.sync()` only for explicit user restore and handle failure. **Validate:** revocation, expiry, unknown product transaction, reinstall and restore on sandbox StoreKit.

11. **Medium — private media has no visible retention/protection policy (privacy/storage).** Original MOVs use Application Support (`CameraOriginalStorage.swift:8-17`), output MOVs use Documents (`PipelineRenderer.swift:1271-1299`), frames use Documents (`RenderQueueViewModel.swift:376-396`), and queue removal deletes only metadata (`:129-136`). No explicit backup-exclusion or file-protection setting was found in production code. **Precondition:** repeated use or row removal; device backups/settings may differ. **Impact:** indefinite residual copies, storage exhaustion and wider backup footprint; do **not** infer files are unencrypted—the platform default and final entitlements were not inspected. **Fix:** design a user-visible retention/delete policy protecting the sole original, apply backup and file-protection policy appropriate to access needs. **Validate:** captures, failed delivery, row removal, low storage, locked-device access and backup inspection.

12. **Low — render LUT parser lacks size and arithmetic limits (bundled-input robustness).** `PipelineRenderer.swift:577-615` accepts arbitrary positive `LUT_3D_SIZE` and compares `size * size * size * 4`, potentially trapping on integer overflow or exhausting memory while appending values; preview parser has explicit size bounds (`CameraPreviewPolicy.swift:78-102`). **Precondition:** malformed/replaced bundled `.cube` (no discovered remote/user LUT import route). **Impact:** local denial of service or render failure, not an external parser exploit on current flow. **Fix:** bounded dimensions, checked products/count, finite-float checks and unsupported-directive rejection. **Validate:** huge, overflowing, malformed and NaN/Inf LUT fixtures.

13. **Low — fallback purchase prices can mislead (release UX/compliance review).** `PurchaseView.swift:108,128` displays hard-coded `$5.00`/`$10.00` if StoreKit products have not loaded, while `StoreManager.swift:43-50` swallows load errors. **Precondition:** offline/store failure or other locale/actual price discrepancy. **Impact:** displayed price may not match actual store sheet; no fraudulent charge shown. **Fix:** show unavailable/loading until localized `Product.displayPrice` is known; validate failure and non-USD locales.
